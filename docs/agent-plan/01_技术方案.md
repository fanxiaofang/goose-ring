# 01 技术方案｜《鹅有一套》H5 验证 / 微信首发 / 抖音后续

## 1. 范围与原则

本文件是 GDD v1.1 的技术实施建议，而非新需求来源。**H5 仅用于横屏原型验证和开发调试；微信小游戏是首发正式发行平台；抖音小游戏在微信首发稳定后再适配。**不开发三套游戏核心代码。当前优先完成静态、普通、机灵三个模式的核心玩法。

核心原则：**可解释的物理结果 > 复杂场景 > 多余功能**。物理判定未通过验收，不能拿美术特效遮盖。

## 美术模型与物理模型分离（P0-3 起必须遵守）

**长期原则：美术可以换皮，物理尺寸不能被美术网格悄悄带着变。**

- 美术模型（以后导入 GLB）只负责外观、材质和动画；物理层另有不可见的简化碰撞代理（身体形状、颈部胶囊段、头部球/胶囊）。
- 套圈也分成可见外观与物理环：当前 16 段胶囊闭合环及其内孔尺寸属于物理基线；换金属材质、加装饰珠或改变渲染细节，不自动改变碰撞环。
- 鹅的物理代理只读取明确的姿态锚点/快照（例如身体根节点、颈根、颈中段、头部中心与朝向），不读取美术网格表面三角形作为命中规则。
- P0-3 先用灰盒和程序动作建立稳定的 `GoosePoseSnapshot` 接口；以后若采用骨骼动画，只需由骨骼适配层把指定骨骼/标记点转换成同一份姿态快照。RingJudge 不直接依赖 GLB 文件名或美术网格。
- 美术交付必须遵循物理尺寸规范：模型头、颈、身体应落在调试显示的碰撞代理范围内。若设计确实要改变头宽、颈粗或比例，作为明确的物理参数变更重新验收，而不是美术导入时自动改变。
- 调试模式必须能同时显示美术模型、头/颈/身体 Collider、套圈 Collider 和 RingJudge 目标轴线；验收时能看出“看起来套中”是否与物理规则一致。

这能让模型换造型、换材质、改贴图时不必重调物理；但如果新造型明显改变实际头颈尺寸，仍须在“保持物理碰撞代理不变”与“接受新的物理尺寸并重测”之间作明确选择，不能承诺任何模型都零调整。

### 2.1 微信首发与包体预算（从现在开始执行）

- **发行顺序**：H5 原型/调试 → 微信小游戏首发 → 抖音小游戏后续适配。
- 不要把 Vite 的 H5 `dist/` 直接当作微信可发布包；微信小游戏没有完整浏览器 DOM，必须通过小游戏入口、Canvas 和平台 Adapter 适配。
- P0-3 后安排一次短小的 **WX-0 技术验证**：把最小场景在微信开发者工具运行，确认 Three.js/WebGL、Rapier WASM 初始化、触摸输入、资源读取、音频/本地存储基本能力，并记录构建包体。若没有可用 AppID，先用可用的测试项目/开发者工具方式验证，并标明限制。
- 当前构建报告中已有约 4.9 MB 的 Vite 单 chunk 体积告警。它**不等于**微信主包最终大小，但说明必须尽早做依赖和打包分析，不能等到发布阶段才处理。
- 微信主包、分包、总包的硬限制可能随平台规则、账号能力和发布方式变化。WX-0 时从最新微信官方文档和开发者工具上传/预览校验取得当前数值；文档不得把旧教程中的 4 MB、20 MB 或 30 MB 写成永久规则。
- 项目内部预算：主包和总包分别控制在当期平台硬限制的 **80% 以内**，至少留 20% 余量；每次微信构建记录主包、每个分包、总包、远程资源大小及开发者工具校验结果。若平台显示的统计口径不同，记录原始截图和口径。
- 主包只放启动必需代码和首屏必需资源；非首屏音效、额外外观等按需分包或作为平台允许的远程资源。不得远程加载/执行脚本；远程资源需配置合法下载域名、版本和缓存。
- 8 只鹅共用同一模型、骨骼和贴图实例资源；三个模式共用同一套行为逻辑。不得为每只鹅或每个模式复制一份模型、Three.js、Rapier 或贴图。
- 优先控制 GLB 面数、贴图尺寸和材质数量；纹理压缩与格式需先验证微信运行时支持，不因追求压缩而造成模型丢贴图或加载失败。


## 3. 场景坐标与相机约定

- 世界：**Y 向上、XZ 为地面**，单位使用“米量级”的统一游戏单位。
- Z 轴正方向为围栏靠玩家一侧，深处为 Z 负；X 左右；玩家投掷起点位于场景近端。
- 当前默认采用透视，垂直 FOV **30°**、俯视 **30°**、偏航 **0°**；该取景已由 P0-L 验收。横向取景同时计算围栏角柱外沿与 5.74 m 站位垫前横木。正交、FOV25°/35°及其他俯视角仅保留调试，不得作为正式镜头基线。
- 摄像机镜头、投掷方向与瞄准求交属于不同计算；**不能仅用屏幕二维落点代替 3D 碰撞**。
- 场景首先做大围栏、干净地面、3D 灰盒鹅头颈、套圈、简单光影；目标区优先，装饰后置。
- H5 的画面取景、DOM 布局、触控坐标共用实际可用区（CSS px）。围栏、鹅群、顶部预留与底部手势矩形执行 [P0-L 规范](05_主游戏场景构图与布局执行规范.md)。H5 的安全区与触摸事件属于宿主适配，世界单位、物理、投掷计算和角色数据由各平台共享。
- 若手机未横屏，提供提示层，而不是让游戏关键元素被裁剪。

## 5. 物理模型：环、鹅、围栏

### 5.1 真实有孔的环

- 可视环：Three.js `TorusGeometry` 或等价薄环。
- 碰撞环：**12～16 个相接的短胶囊段/小凸体围成闭合环**，固定在同一个动态刚体上（数量待压测）。内孔必须真实空出，**不能用一个圆盘碰撞体**。
- 圈的动态刚体包含质量、线速度、角速度、摩擦、弹性；合法碰撞覆盖地面/围栏/鹅头/颈/身体。
- 固定 timestep，例如 `1/60 s`，渲染使用插值，帧率下降时限制 catch-up 次数；高速情况按需启用 CCD / substep。
- 接触事件、debug draw 和性能统计必备；若多个胶囊段引起跳动，记录撞击序列并调碰撞体，而非直接删除碰撞。

### 5.2 鹅头颈

- P0：球头 + 圆柱/胶囊颈 + 粗略身体，头宽、颈宽与圈内径都可调。
- P0-3：鹅颈上下/左右摆动使用**运动学碰撞体**或按物理引擎支持的更新方式跟随视觉姿态；不能静止 collider + 视觉摆头。
- 后续 GLB：以骨骼世界矩阵更新可简化的头/颈 Collider；每个物理 step 前刷新运动学目标位姿，step 后同步渲染。
- 8 只鹅先使用低成本分离 + 边界修正，不要上真实动物骨骼动力学。

### 5.3 场景障碍

地面、围栏需要固定 Collider；视觉栏杆不可穿透。摊主、食槽、水盆在 P3 加入前保留放置规划；**实际添加视觉障碍时必须同时明确是否有实体碰撞**。

## 6. RingJudge 的规则与事件边界

### 6.1 状态机

P0-2 已签收的当前状态机为：

`FLYING → ENTER_NECK → SETTLING → CAUGHT | MISSED`。

- **ENTER_NECK**：圈沿自身法线向下运动；必须先记录鹅头从环平面下方向上穿越，再记录颈轴由下向上穿越，且颈轴穿越点落在环内孔内。
- **SETTLING**：入颈后检查竖直颈轴与环平面的交点是否仍在内孔；持续 **0.25 s 起步**（可经重放实测上调，见 [04 D-20261126-008](04_决策与参数.md)）后判成功，滑出内孔判 `slip`。稳定期不再单独按倾斜判负。
- **CAUGHT**：一次投掷最多一只；多鹅同 tick 取穿越点距环轴最近者，不同 tick 取最早入颈者；单个判定实例幂等。已退场鹅通过 `excludeIndices` 排除。
- **MISSED**：落地、未入颈时的撞头/撞身归因、侧穿、稳定期滑脱等。
- 头/身接触不立即判负；它们只在未入颈后落地或静止时用于失败归因。静止兜底是 P0-2 已签收口径的一部分。

P0-2 使用几何穿越近似，不模拟真实环与颈部的接触力。**P0-3 只把头/颈目标姿态改为逐物理步实时输入，不得借机重做判定规则。**

### 6.2 事件流

`PointerReleased → ThrowRequested → RingSpawned → PhysicsStepped → RingJudgeResolved → RoundFeedback / GooseAndRingRetire → UIUpdate`。

- `ThrowRequested` 必须有唯一 throwId；切后台、暂停、取消/松手合法性要有清晰语义。
- P0-2 当前只更新本盘临时计数并移除已套鹅/套圈，不实现正式历史存档。P2 才由可靠存储服务提交正式成绩；动画/音频消费结果事件，不负责加分。

## 7. 投掷输入与轨迹辅助

- 现有操作支持按住计时、下拉或斜拉蓄力和向前甩投，横向分量用于瞄准，松手时确认出手。P0-L 的手持圈触摸区和底部兜底区继续作为合法起手范围。
- `ThrowGesture` 使用起手时的尺寸、位置和输入时间解析三种方式。H5 处理 Pointer Events 和捕获，`buildPlayerThrow` 生成预览与真实出手共用的初态。预览线阻尼读取当前实投参数，重放保存原投掷的物理配置。P0-A 的自动测试及真机待测项见阶段报告。
- `AimMapper` 输入使用归一化屏幕坐标和手势向量；输出投掷初速度、朝向、可选初始旋转。支持鼠标模拟，但最终必须真实手机触控。
- 预测轨迹是**按同一重力、同一初速度的无碰撞轨迹**，地面落点来自 3D 物理世界的几何求交；不应与实投弹道使用两套互相矛盾的初速度映射。
- `AssistLevel`：`full` / `landing` / `off`；静态场引导默认 full，普通/机灵场的正式辅助规则按 GDD 与后续决策执行。单鹅调试直达不是玩家练习模式。
- 预测环仅表示**无碰撞的首次地面落点**，不能宣传为必中或实时追踪鹅的位置。
- 若实际抛物线与预测差距过大，先查初速度、重力、初始姿态和世界坐标，不通过临时屏幕偏移修补。

## 8. 鹅 AI（P0-4 尽快完成普通场/机灵场）

数据：`obedience`、`awareness`、`agility`、`latencyMin/Max`、`walkSpeed`、`dodgeCooldown`，三类原型参数来自 GDD v1.1，不代表真实品种行为。

- P0-3 只做一只灰盒鹅的可预测头颈动作和动态判定同步；不做漫游 AI。
- P0-4 实现普通/机灵场共享的轻量活动逻辑：局部目标漫游、边界回避、近鹅分离、投圈威胁预测、察觉概率、反应延迟、低头/侧躲与冷却。先做 8 只，不做完整 Boids。
- 普通场和机灵场只通过参数配置区分察觉率、反应延迟、躲避速度/幅度和冷却；不能写两套 AI，也不能靠随机数让机灵场无解。
- P1 将静态场、普通场、机灵场接入完整可玩模式循环；P2 再做新手引导、正式本地存档和经济模拟。
- 执行顺序：预测圈的威胁 → 按察觉率决定是否感知 → 等待个体反应延迟 → 做可见动作（低头/歪头/侧移）→ 冷却；不可最后一瞬间跳到完美躲避位置。
- Debug 事件写 `gooseId/throwId/perceived/latency/action/AIseed`，便于复现“作弊闪避”。

## 9. 正式进度与本地持久化（P2）

### 9.1 状态归属

- 单鹅调试：已降级为 `?geese=single` 调试直达（2026-11-26），不扣正式圈、不写正式 Board、不计正式累计；`practiceRingsRemaining` 已废弃。
- 正式：静态/普通/机灵三种模式各保留独立 Board 和分模式累计；`lifetimeCaught` 为三个正式模式累计之和。
- Board：`boardId`、`seed`、`mode`、`gooseIds`、`caughtGooseIds`、`throwsUsed`、`clearedAt`；允许跨天继续，手动换盘只丢清摊进度，不撤销已得的历史数。
- `accuracy = lifetimeCaught / totalThrows`（累计口径）；未投圈显示 `—`，不是 0% 或 NaN。
- 清摊发生时只记清摊次数，不再批量加鹅。

### 9.2 单次“套中”原子落盘

**核心不变量**：同一个 board 的同一个 gooseId 只加一次；同一个 throwId 只能结算一次；当前盘已套数、模式累计、历史累计必须一致。建议把这些内容做成**单份版本化快照**或 IndexedDB 事务；写完再发布“永久到账”成功提示。写失败提示待保存、重试，不能无证据写 UI 永久 +1。

每次提交后可做开发态断言：`lifetimeCaught === caughtStatic + caughtNormal + caughtClever`，`Board.caughtCount === caughtGooseIds.length`，同一 `throwId` 与同一 Board 内 gooseId 不重复入账，`saveVersion` 能向前兼容。

**意外中断与防作弊之间存在未定取舍**：GDD v1.1 建议在未结算投掷中断时恢复圈、撤销未确认投掷；这在纯本地原型中用户友好，但正式排行榜/经济场景可能被“看着快失误就退出”利用。P2 必须实现可配置的中断策略、写日志并标记未定；正式运营需服务端权威校验或规则调整，不得把原型策略假定成防作弊方案。

### 9.3 时间与排行

H5 首版只做个人总数、静态/普通/机灵分模式总数、正式投圈数和清摊统计的本地存储。单鹅调试数据不进入正式存档。月榜/历史榜可做占位说明，**不做假在线排名**。跨用户排行、运营日领取和广告收益需要平台与可信后端/平台服务；本地修改时间不能作为可靠结算依据。

## 10. 经济与平台边界（P2 只模拟；微信为首发）

- 每日 **20 庙会币**、`20 币→20 圈`、`50 币→60 圈` 目前是 GDD 优先候选，不是锁死运营价格。
- P2 可实现本地配置化的“币/正式圈”演示，或只做资源模拟；必须保持单鹅调试直达、正式圈和币相互隔离；调试投掷不得消耗或写入正式资源。
- 平台接口建议最少：`StoragePort`、`TimePort`、`AdsPort`、`SharePort`、`LeaderboardPort`；H5 阶段实现 Web Adapter，微信首发前实现 WeChat Adapter，抖音后续实现 Douyin Adapter。游戏核心不能直接引用 `wx`、`tt`。
- 广告相关按钮：原型未接入时隐藏或清晰标记“未开放”，**不能虚构广告已展示并发放奖励**。
- H5 DOM HUD 可用于快速原型，但微信小游戏不能假设存在完整 DOM；从现在开始把 HUD 状态/交互与 DOM 渲染分离，WX-0 验证 Canvas 渲染和输入路径。

## 11. 性能与观察性

- 手机横屏优先，核心视口 **844×390 与 667×375 CSS px**。1280×720 用于开发截图。围栏按完整轮廓计算占宽/占高；手机安全区和关键元素净空按 [P0-L 规范](05_主游戏场景构图与布局执行规范.md) 验证。
- 优先在手机争取稳定 30 FPS，物理模拟使用固定 timestep（如 60Hz）；低端机帧率下降不能让投掷更易/更难。
- Debug 面板至少：相机角度、轨迹辅助、环内径、环厚、质量、重力、速度、摩擦、弹性、鹅头宽、颈宽、头颈姿态、CCD、碰撞线框、RingJudge 状态、当前 FPS/step 时间、当前 seed。
- 自动截图/录屏/回放关键场景（至少：成功套入、撞头、侧穿、低头避让、围栏碰撞、低帧率）。正式 UI 隐藏调试控件。

## 12. 依赖与升级风险

- 先本地执行一次安装与构建，检查所用版本 API；把安装版本记在提交/报告，不盲信网上过期代码。
- Three.js、Rapier 与 Vite 独立升级时先运行受影响的碰撞/构建回归，不为小版本变更无条件执行大型压力测试。
- H5 的 DOM/Canvas、WebAudio、WASM、文件读取和生命周期与微信小游戏并非完全相同；必须在三模式开发早期做 WX-0 运行验证。不能把“桌面 H5 正常”当成“微信可发布”。
- 抖音小游戏不是当前适配目标；微信首发稳定后复用核心逻辑，单独验证 Douyin Adapter、包体与平台 API。
