00_使用说明.md

使用方法

《套大鹅》Agent 执行包 v0.1｜从 GDD 到可玩 H5

版本：2026-11-22。配套来源：GDD_v1.1_设计基线.md（原样复制），其规则优先于本文。
目标：让 Codex / Google AI Studio 逐关口实现并验证，而不是一条提示词生成完整游戏。
当前交付物是执行资料，不是已经完成的游戏代码。

现在该怎么用

  1. 下载并解压整个执行包，放到游戏项目根目录的 docs/agent-plan/（也可以先单独放在空目录）。
  2. 将本包的 AGENTS.md 放到项目根目录，让 Codex 阅读它；如果已有 AGENTS.md，请合并，不要直接覆盖。
  3. 把 GDD_v1.1_设计基线.md、01_技术方案.md、02_阶段任务.md、03_验收测试.md 一起交给 Agent；第一轮只执行 prompts/P0-0_初始化与场景.md。
  4. 每完成一个阶段：本人打开网页试玩 → 核对验收证据 → Git 提交 → 继续下一阶段。没有实际运行/测试结果，不得宣称“完成”。
  5. 04_决策与参数.md 用来记录真实测试值、未定问题；数值不应直接写死在散落的脚本中。

先做什么、后做什么

里程碑 只需证明什么 通过后才能做什么
P0-0 技术底座 H5 横屏场景可跑、相机可调、物理初始化成功 加入套圈物理
P0-1 套圈真实物理 有孔的圈飞行/落地/碰栏，不是实心圆盘 加入鹅头颈障碍
P0-2 套入判定 正上方合理套入能成，撞头/侧穿不能成 加入活动鹅与同步碰撞体
P0-3 活动与稳定性 鹅颈动作+物理同步、低帧率无明显穿模 新手练习
P1 练习可玩版 有限练习圈、轨迹预测、暂停恢复、教学反馈 正式两模式
P2 正式游戏循环 8 鹅盘、正式库存、普通/机灵、成功即时记账、清摊/跨天续盘 P3 角色与氛围

不在 P0–P2 直接做：正式精美场景、完整 3D 骨骼资产、完整鹅群 Boids、摊主指挥、真实广告、分享奖励、全服/省份榜、多人联机、后端、生产版微信/抖音构建。

新手应该了解的三件事

  • “可以跑” ≠ “物理正确”：模型好看但穿模、判定解释不通，P0 就不能通过。
  • “有按钮” ≠ “功能完成”：需要实际点击，验证资源扣减、出错恢复、刷新页面的数据一致性。
  • “模拟器能跑” ≠ “微信/抖音能发”：早期写平台隔离层，实际构建与 SDK 适配另立任务；不承诺 H5 原封不动移植。

运行与验收工作流

Agent 应在项目新建后按实际环境确认 Node/npm 版本要求，安装依赖并提交 lockfile；常规命令预计为：

npm install
npm run dev -- --host 0.0.0.0
npm run build
npm run test

npm run test 由 Agent 在项目配置内补齐。若 Node/npm 或浏览器无法运行，请明确报告原因，不要凭空编造测试结果。

来源与优先级

  1. GDD v1.1 的 【确定】 不得擅改。
  2. 本包的技术实验措施和【建议】是可调整实现方案；每次调整要记录理由与风险。
  3. GDD 的 【待测】/【待定】 必须配置化或保留 TODO，不许冒充已确定需求。
  4. 若技术实现证明当前物理设计不可行，应明确给出“失败证据 + 替代方案 + 所牺牲的真实性”，先交人决策，不得偷偷改成碰到鹅就算套中。

你是我这款 H5 小游戏《套大鹅》的技术负责人和结对开发 Agent。我的游戏开发经验很少，我会用自然语言描述效果，你负责拆分任务、实现、运行、测试并给出明确的操作方法。

请先认真阅读项目中的以下文件（如果不在根目录，则去 docs/agent-plan/ 下查找）：

  • GDD_v1.1_设计基线.md：唯一产品需求基线。
  • AGENTS.md：工程协作规则。
  • 00_使用说明.md
  • 01_技术方案.md
  • 02_阶段任务.md
  • 03_验收测试.md
  • 04_决策与参数.md

本次只执行 prompts/P0-0_初始化与场景.md；绝对不要自动完成 P0-1、P1、P2 或增加美术、商城、排行榜、广告。

你的工作方式：

  1. 先检查工作目录、Node/npm、已有文件和 Git 状态；如为空项目则初始化 Vite + TypeScript + Three.js + Rapier 3D。不要随意覆盖已有代码。
  2. 简述本次要改什么、有哪些风险；对不影响 P0 的未知美术或玩法细节直接采用配置化实验值，不要停下来问我一堆问题。
  3. 实际实现一个横屏固定正交相机场景（38° 默认，可切 30/45°），包含大围栏、地面、物理世界和调试面板。
  4. 实际运行、构建、进行基本自测（如果环境允许）。
  5. 给我一个尽可能简单的本地运行步骤和手机浏览器试玩方法；标注需要我手工验收的事项。
  6. 报告文件变更、实际运行/测试证据、未解决问题，并停下等待我确认。

硬要求：真实 3D 空间（Y 向上、XZ 地面）；不可用纯平面 2D 冒充纵深；不允许用无来源的素材冒充已完成美术；测试做不到就说没有测试；本阶段不许生成整款游戏。文档中的【待测】数值只能当默认实验参数。

01_技术方案.md

技术架构

01 技术方案｜《套大鹅》H5 P0–P2

1. 范围与原则

本文件是 GDD v1.1 的技术实施建议，而非新需求来源。首版横屏 H5，保留向微信/抖音小游戏迁移的技术边界；不现在开发三套平台代码。主要验证：真实 3D 套圈、会动的鹅颈、合理套中判定、正式即时存档。

核心原则：可解释的物理结果 > 复杂场景 > 多余功能。物理判定未通过验收，不能拿美术特效遮盖。

2. 技术栈与环境

领域 起点 选择原因 / 约束
H5 TypeScript + Vite vanilla-ts 无需 React 游戏框架，构建快
3D 渲染 Three.js OrthographicCamera、模型、debug、渲染
物理 @dimforge/rapier3d-compat WASM 跨常见 Web 打包环境；先测试 Vite 打包及手机兼容
单测 Vitest 纯逻辑、状态转移、数据记账、几何守卫
可选 UI 自动化 Playwright 横屏尺寸、触摸、设置与刷新烟雾测试
资产 P0 几何体 / P3 才考虑 GLB 物理优先，不让美术阻塞
存储 P1/P2 版本化快照（本地） 先在单端 H5 验证；正式排行须服务端

初始项目命令（Agent 应按当前官方文档与本地 Node 版本验证，不要凭空假设已安装）：

npm create vite@latest tao-da-e -- --template vanilla-ts
cd tao-da-e
npm install three @dimforge/rapier3d-compat
npm install -D @types/three vitest
npm run dev -- --host 0.0.0.0

首次跑通后固定依赖版本、提交 package-lock.json。若 rapier3d-compat 在某平台构建失败，记录故障后再比较其他官方发行包，不要随意添加多个物理引擎。

3. 场景坐标与相机约定

  • 世界：Y 向上、XZ 为地面，单位使用“米量级”的统一游戏单位。
  • Z 轴正方向为围栏靠玩家一侧，深处为 Z 负；X 左右；玩家投掷起点位于场景近端。
  • 固定 OrthographicCamera，初始俯视角相对水平面 38°，测 30° / 38° / 45°，偏航 0° 起。
  • 摄像机镜头、投掷方向与瞄准求交属于不同计算；不能仅用屏幕二维落点代替 3D 碰撞。
  • 场景首先做大围栏、干净地面、3D 灰盒鹅头颈、套圈、简单光影；目标区优先，装饰后置。
  • HUD 需要按横屏安全区布局，底部手势热区必须独立，不可被上层 DOM 事件拦截。
  • 若手机未横屏，提供提示层，而不是让游戏关键元素被裁剪。

4. 工程代码分层（建议目录）

src/
  app/             # 启动、销毁、主循环和应用状态
  scene/           # Camera、Arena、DebugOverlay、RenderView
  input/           # PointerController、AimMapper、TrajectoryPreview
  physics/         # RapierWorld、RingBody、ArenaColliders、PhysicsDebug
  ring/            # ThrowState、RingJudge、RingVisualState
  goose/           # GooseEntity、GooseColliderRig、GooseAI、GooseAnimation
  board/           # BoardService、BoardGenerator、ModeConfig
  progression/     # PlayerStats、ThrowLedger、SaveRepository
  economy/         # 练习额度、正式圈与币（P2 只模拟库存）
  ui/              # HUD、Pause、Help、Settings、Result
  platform/        # PlatformPort、WebPlatform (微信/抖音暂不实现)
  config/          # 可调参数、默认数值、调试开关
  tests/           # 规则单测 / 场景回归脚本
public/assets/     # 后续有许可的声音/贴图/GLB

一个阶段不必创建所有空文件和空服务；实际用到才建立。不要在 P0 加入完整业务架构、状态框架或后端。

5. 物理模型：环、鹅、围栏

5.1 真实有孔的环

  • 可视环：Three.js TorusGeometry 或等价薄环。
  • 碰撞环：12～16 个相接的短胶囊段/小凸体围成闭合环，固定在同一个动态刚体上（数量待压测）。内孔必须真实空出，不能用一个圆盘碰撞体。
  • 圈的动态刚体包含质量、线速度、角速度、摩擦、弹性；合法碰撞覆盖地面/围栏/鹅头/颈/身体。
  • 固定 timestep，例如 1/60 s，渲染使用插值，帧率下降时限制 catch-up 次数；高速情况按需启用 CCD / substep。
  • 接触事件、debug draw 和性能统计必备；若多个胶囊段引起跳动，记录撞击序列并调碰撞体，而非直接删除碰撞。

5.2 鹅头颈

  • P0：球头 + 圆柱/胶囊颈 + 粗略身体，头宽、颈宽与圈内径都可调。
  • P0-3：鹅颈上下/左右摆动使用运动学碰撞体或按物理引擎支持的更新方式跟随视觉姿态；不能静止 collider + 视觉摆头。
  • 后续 GLB：以骨骼世界矩阵更新可简化的头/颈 Collider；每个物理 step 前刷新运动学目标位姿，step 后同步渲染。
  • 8 只鹅先使用低成本分离 + 边界修正，不要上真实动物骨骼动力学。

5.3 场景障碍

地面、围栏需要固定 Collider；视觉栏杆不可穿透。摊主、食槽、水盆在 P3 加入前保留放置规划；实际添加视觉障碍时必须同时明确是否有实体碰撞。

6. RingJudge 的规则与事件边界

6.1 状态机

READY → FLYING → CONTACT / ENTER_NECK → SETTLING → CAUGHT | MISSED。

  • CONTACT：与物体碰触，不等于成功。
  • ENTER_NECK：圈的真实开放内孔从鹅头上方合理越过头部，已进入颈部区域；必须使用穿越历史、环平面方向、物理接触证据，不能只根据二维屏幕重叠。
  • SETTLING：处于正确位置并经过 0.4～0.7 s 待测稳定期；滑脱则失败。
  • CAUGHT：一次投掷最多一只、一次鹅盘同只最多一次，触发轻柔的环挂脖表现/视觉淡出；P2 才入正式历史账户。
  • MISSED：落地、撞头未套入、碰身、侧穿、滑脱、越界等。

建议判定关口（几何 + 真实物理）：

  1. 圈的平面及开口大小足以容纳头部横截面，不与头部 solid collider 发生非法穿透。
  2. 圈从鹅头上方进入，由前后两次物理位姿证明发生有效的“头上方 → 颈部高度”穿越；不是瞬移后落在颈部。
  3. 颈轴线穿过环的内孔，环姿态在容忍角度内，实际接触序列符合物理。
  4. 稳定期圈未脱离、没有明显非法相交，才进入 CAUGHT。
  5. 对旋转颈部使用骨骼/运动学 Collider 的实际世界位姿，不拿固定竖直轴心硬判。

这些只是实验性判定规范。如果真实软环的几何/物理难以稳定近似，Agent 必须记录失败案例，提出候选方案（例如物理环 + 几何穿越守卫 + 命中后视觉挂圈），说明准确性取舍，不得默默做“碰到鹅计分”。

6.2 事件流

PointerReleased → ThrowRequested → RingSpawned → PhysicsStepped → RingJudgeResolved → PracticeFeedback | FormalCaughtCommit → UIUpdate。

  • ThrowRequested 必须有唯一 throwId；切后台、暂停、取消/松手合法性要有清晰语义。
  • RingJudgeResolved 只能输出一次最终状态。动画/音频消费事件，不负责加分；保存服务是正式成绩的唯一写入点。

7. 投掷输入与轨迹辅助

  • 游戏目标操作模型：底部手势区按住、向后拉动蓄力、左右调整方向、松手投掷。
  • AimMapper 输入使用归一化屏幕坐标和手势向量；输出投掷初速度、朝向、可选初始旋转。支持鼠标模拟，但最终必须真实手机触控。
  • 预测轨迹是按同一重力、同一初速度的无碰撞轨迹，地面落点来自 3D 物理世界的几何求交；不应与实投弹道使用两套互相矛盾的初速度映射。
  • AssistLevel：full / landing / off；练习默认 full，正式是否开放待定。
  • 预测环仅表示无碰撞的首次地面落点，不能宣传为必中或实时追踪鹅的位置。
  • 若实际抛物线与预测差距过大，先查初速度、重力、初始姿态和世界坐标，不通过临时屏幕偏移修补。

8. 鹅 AI（P2 才做基础，后续逐步加）

数据：obedience、awareness、agility、latencyMin/Max、walkSpeed、dodgeCooldown，三类原型参数来自 GDD v1.1，不代表真实品种行为。

  • P0 鹅静止；P0-3 一只鹅做可预期头颈动作；P1 3～5 只低动态鹅；P2 8 只缓慢移动、差异化察觉/冷却、机灵参数。
  • 执行顺序：预测圈的威胁 → 按察觉率决定是否感知 → 等待个体反应延迟 → 做可见动作（低头/歪头）→ 冷却；不可最后一瞬间跳到完美躲避位置。
  • 鹅群规模在手机上先只做随机漫游、分离、边界约束；Boids 完整聚合和摊主指挥放 P3/以后。
  • Debug 事件写 gooseId/throwId/perceived/latency/action/AIseed，便于复现“作弊闪避”。

9. 正式进度与本地持久化（P2）

9.1 状态归属

  • 练习：独立 practiceRingsRemaining，不计正式累计。
  • 正式：普通/机灵两种模式共用 formalRings，各保留独立 Board 和 mode 累计；totalCaught 为两者加和。
  • Board：boardId、seed、mode、gooseIds、caughtGooseIds、throwsUsed、clearedAt；允许跨天继续，手动换盘只丢清摊进度，不撤销已得的历史数。
  • accuracy = totalCaught / totalThrows（累计口径）；未投圈显示 —，不是 0% 或 NaN。
  • 清摊发生时只记清摊次数，不再批量加鹅。

9.2 单次“套中”原子落盘

核心不变量：同一个 board 的同一个 gooseId 只加一次；同一个 throwId 只能结算一次；当前盘已套数、模式累计、历史累计必须一致。建议把这些内容做成单份版本化快照或 IndexedDB 事务；写完再发布“永久到账”成功提示。写失败提示待保存、重试，不能无证据写 UI 永久 +1。

每次提交后可做开发态断言：totalCaught === caughtNormal + caughtClever，Board.caughtCount === caughtGooseIds.length，saveVersion 能向前兼容。

意外中断与防作弊之间存在未定取舍：GDD v1.1 建议在未结算投掷中断时恢复圈、撤销未确认投掷；这在纯本地原型中用户友好，但正式排行榜/经济场景可能被“看着快失误就退出”利用。P2 必须实现可配置的中断策略、写日志并标记未定；正式运营需服务端权威校验或规则调整，不得把原型策略假定成防作弊方案。

9.3 时间与排行

H5 首版只做个人总数/模式总数/投圈数/清摊/练习资源本地存储。月榜/历史榜可做占位说明，不做假在线排名。跨用户排行、运营日领取和广告收益需要平台与可信后端/平台服务；本地修改时间不能作为可靠结算依据。

10. 经济与平台边界（P2 只模拟）

  • 每日 20 庙会币、20 币→20 圈、50 币→60 圈 目前是 GDD 优先候选，不是锁死运营价格。
  • P2 可实现本地配置化的“币/正式圈”演示，或只做资源模拟；必须保持练习资源、正式圈和币相互独立。
  • 平台接口建议最少：StoragePort、TimePort、AdsPort、SharePort、LeaderboardPort；P2 只实现 Web/Stub，不能在游戏核心引用 wx、tt。
  • 广告相关按钮：原型未接入时隐藏或清晰标记“未开放”，不能虚构广告已展示并发放奖励。
  • H5 DOM HUD 可用，但小游戏真机未必有 DOM；将 HUD 交互控制与 DOM 渲染拆开，未来替换 Canvas/平台原生实现。

11. 性能与观察性

  • 目标横屏视野：16:9 起，兼容 18:9 和安全区；鹅栏视觉占比目标约 60%～70%（待测）。
  • 优先在手机争取稳定 30 FPS，物理模拟使用固定 timestep（如 60Hz）；低端机帧率下降不能让投掷更易/更难。
  • Debug 面板至少：相机角度、轨迹辅助、环内径、环厚、质量、重力、速度、摩擦、弹性、鹅头宽、颈宽、头颈姿态、CCD、碰撞线框、RingJudge 状态、当前 FPS/step 时间、当前 seed。
  • 自动截图/录屏/回放关键场景（至少：成功套入、撞头、侧穿、低头避让、围栏碰撞、低帧率）。正式 UI 隐藏调试控件。

12. 依赖与升级风险

  • 先本地执行一次安装与构建，检查所用版本 API；把安装版本记在提交/报告，不盲信网上过期代码。
  • Three.js、Rapier 与 Vite 独立升级时先运行碰撞和 UI 回归测试。
  • H5 的 DOM/Canvas、WebAudio、WASM、加载方式与微信/抖音并非完全相同；发布前需要针对目标平台制作明确的运行时适配实验。抖音开发文档说明其小游戏运行时没有完整浏览器 BOM/DOM。

02_阶段任务.md

执行任务拆分

02 Agent 执行任务与阶段关口（P0–P2）

执行原则：完成一个、验收一个、再开始下一个。 下列任务顺序是实现依赖，不是玩家关卡。对应 GDD v1.1 的 P0–P2，不意味着 P3/P4 已定或已开发。

通用交付要求

每个任务结束，Agent 必须汇报：

  1. 本次实际改动文件与功能；如修改既有结构，说明为何必要。
  2. 启动/构建/测试的真实命令及输出摘要；做不到的明确写原因。
  3. 如何人工复现正例、反例；提供至少 2 张截图或说明录屏保存位置（如果执行环境允许）。
  4. 可调参数清单、未解决问题和实际风险。
  5. 停在当前阶段，不自动进入下一阶段。

每步确保 Git 可回退；失败路径也是验收目标。

P0-0：创建工程、横屏场景与物理底座

目标：证明 Three.js + Rapier + Vite 在 H5 本地正常运行。

范围：初始化 vanilla-ts；创建 Three scene、OrthographicCamera（俯视角可切 30/38/45°）、地面、围栏（视觉与 Collider 同步）、Rapier WASM 初始化、固定时间步主循环、基础调试面板、鼠标/触控基本事件；屏幕不是横屏时提示旋转。

排除：没有鹅 AI、没有玩法、没有广告/商店/UI 大厅、没有正式美术。

验收：浏览器桌面/移动模拟可见宽围栏；调整镜头不破坏坐标；物理地面碰撞有效；npm run build 与 TS 检查通过；控制台无持续错误；开发态能看物理碰撞调试信息。

关口：能安全生成一个测试刚体落到地面，不穿透；若 Rapier WASM 加载失败，先修再继续。

P0-1：套圈真实物理与飞行操作

目标：可投掷一个具有空孔、体积与倾角的物理圈。

范围：有孔环体复合 Collider；出手初速度；重力、摩擦、弹性、弹跳和碰栏；底部拖拽/松手投掷；发射起点；圈的销毁回收；显示固定步、环体 Collider、速度与旋转，必要时 CCD。

排除：此时暂不判断套中；不加复杂鹅模型。

验收：多种力度可产生连续可重复的飞行距离；碰地有响应、碰围栏可弹/停且不透明穿透；圈穿过无障碍空洞时不被假圆盘挡住；多次投掷后资源清理正常；不能把视觉圈做得和 Collider 明显不一致。

关口：P0-1 至少录下 3 种碰撞情形（地面、栏杆、不同初始倾角）。若环状 Collider 性能或稳定性严重不足，提交实验数据与备选实现，等待决策。

P0-2：几何鹅头/颈 + RingJudge 状态机

目标：实现只有合理地套入鹅颈才算成功。

范围：几何头（球形）、颈（胶囊/圆柱）、身体，Collider 与视觉对应；RingJudge 状态机；头部上方→颈部的穿越事件；稳定时间；合法/非法命中；开发态日志、测试场景。

排除：暂不做复杂 AI、精美鹅或历史累计。

验收用例：

  • 正面落入、环内孔满足尺寸、稳定超过配置时长 → 成功 1 次。
  • 直接碰头、碰身、环边擦过 → 不成功。
  • 环从侧面穿到脖子/从背后穿模 → 不成功、并可解释为何。
  • 在稳定期滑落 → 不成功。
  • 一个环碰到两个鹅 → 最多 1 次有效成功。
  • 同一次 throwId 多次接触事件 → 只结算 1 次。

关口：至少 5 种可手动触发的正反场景有文字/截图证据；若判定不得不采用近似方案，必须标明真实物理和规则补偿的边界。

P0-3：鹅头颈动作、碰撞同步与压力测试

目标：圈可以和真实运动的头颈互动，不出现视觉与 Collider 不一致。

范围：一个鹅头做低头/歪头预设运动，Collider 同步；鹅与围栏/鹅与鹅简化阻挡；更新顺序统一；暂停/后台恢复；10～100 次压力测试脚本、低帧率模拟；相机 3 档对比。

验收：移动脖子时可见与实际碰撞一致；撞击面不会变成隐形墙；鹅主躯干不穿其他鹅；渲染降到 15–30 FPS 时物理结果不随 FPS 变形；圈落地不会越栏；测试记录异常次数。

关口：若有明显物理穿模或“命中假象”，停止增加游戏内容，先定位。

P1：可用的新手练习场

目标：首次试玩者能在手机横屏理解怎样扔圈。

范围：3～5 只静止/轻摆头的鹅；练习开始入口；full/landing/off 轨迹与预测落点辅助；首次配置化 30 个练习圈（50 为对照值）；练习投圈扣减、退出/刷新恢复；友好的成功/失败反馈；设置中的最小音量/静音；帮助说明。

必须区分：开发者可通过 debug 无限投圈，正式玩家练习额度有限；练习无正式总数、排行榜、币库存写入。

验收：初次打开有清楚教程；触摸/鼠标拖拽方向和力度可学；轨迹与无障碍地面落点相符；练习圈正确扣减；关闭网页重新打开，额度剩余正确；没有无限练习漏洞；能从设置关闭鹅叫/环境声占位通道（如果对应声音已加入）。

关口：真人手机实测后再把 P1 称为“可玩”。如果 30 个圈不够学会投掷，先对照 50，不得擅自开放无限。

P2：正式游戏核心闭环（不接真实广告）

目标：正式套中立即记 1 只、保存、支持清摊和跨天继续。

范围：普通/机灵模式，共用正式圈库存，各自独立 Board；每盘初始 8 鹅（可调）；基础漫游、察觉/反应延迟/躲避冷却（按 GDD 的参数原型）；一次投掷对应唯一 throwId；CAUGHT 在单次原子本地事务更新玩家历史累计和盘面；清摊/漂亮清摊；换盘、切模式、暂停恢复；个人准确率、按模式总数；简单大厅/HUD/结算卡；币和兑换配置化模拟（可根据进度独立开关，不引入真实广告）。

不做：摊主指挥、完整 Boids、真实排行、真实微信/抖音 SDK、朋友圈立即分享领币、省份榜。

验收：

  • 普通鹅套中 → 普通累计 +1、总数 +1；机灵同理。
  • 练习套中 → 正式累计完全不变。
  • 单只正式套中后立即刷新 → 历史数据和 Board 一致。
  • 重复触发一次 hit → 不能双加；换盘和清摊不能二次加数。
  • 8/8 清摊 → 清摊次数 +1，累计不额外 +8；可新盘。
  • 中途退出明天再来 → 继续同一盘、库存和已套中保持。
  • 圈数不足 → 可以暂停/退出/展示补给占位，不强制广告。
  • 余额兑换同一命令重复执行 → 不得重复送圈或扣币；P2 仅模拟政策。

关口：P2 才成为内部 H5 玩法原型。即使 P2 通过，也不能声称已满足微信/抖音发布条件。

P3 / P4（只列后续入口，本包不安排实施）

  • P3：3D 鹅骨骼/表情、庙会场景与宽敞围栏、食盆/水盆、小招牌、摊主在围栏安全带走动、友好俏皮声效、动物舒适度测试。
  • P4：平台运行时验证、广告与分享政策、真实排行榜、运营日币领取/服务端记账、发布适配和合规审核。

03_验收测试.md

验收与测试

03 验收与测试｜让“看起来能玩”变成“确实可信”

目的：给本人和 Agent 一套可以操作、可以复现、可以判断过/不过的标准。P0–P2 执行期间逐渐实现；不要求 P0 就通过全部业务测试。

1. 标准测试环境

  • 电脑浏览器：能用鼠标复现拖动投圈，检查控制台、WebGL/WASM 加载与 FPS。
  • 横屏手机：至少一部真实手机，测试触摸热区、拖动、音频、屏幕安全区、切后台恢复。模拟器不能替代真机手感。
  • 可调相机：30°、38°、45°；16:9 与更宽横屏可视区域。
  • 开发态开关：碰撞线框、路径线、鹅头颈轴线、RingJudge 状态、飞行速度、Throw ID / Goose ID、固定物理 tick、随机 seed、物理慢动作。
  • 固定种子：至少 3 套可重复场景；禁止用“随机结果刚好通过”掩盖不稳定。

5. 体验与动物友好验证

找 5–10 位使用真实手机的试玩者，记录而非预设结果：

  1. 是否无需长说明就懂得怎样拉动/松手？
  2. 玩家套不中时，能否准确解释偏短、偏远、撞头还是鹅躲开？
  3. 辅助轨迹是否有帮助？30 个练习圈是否太少？
  4. 普通场与机灵场差别是否明显、可学习？
  5. 套中后鹅的反应是否轻松、友善，是否有人觉得在伤害动物？

AGENTS.md — 《套大鹅》项目协作规约

项目目标

制作中国庙会氛围、横屏正交视角的轻量 3D 物理套圈 H5 原型。鹅是虚构、友好、无伤害的互动角色。首版必须证明物理套入鹅颈的手感，而不是制作精美介绍页。

需求唯一基线

先阅读 docs/agent-plan/GDD_v1.1_设计基线.md、docs/agent-plan/01_技术方案.md、docs/agent-plan/02_阶段任务.md、docs/agent-plan/03_验收测试.md。若仓库实际路径不同，先确认文件位置，不默默跳过。需求冲突时，记录在 docs/agent-plan/04_决策与参数.md 并明确提出。

工作约束

  1. 每次只实现一个任务；先列影响文件、方案、验收条件；再动代码。
  2. 只做当前阶段功能，不得擅自加入广告、排行榜、登录、商城、外星人摊主、复杂美术与无关框架。
  3. 优先 TypeScript + Three.js + Rapier 3D + Vite；遵循版本锁定、单份物理状态源、固定物理时间步。
  4. World 坐标统一：Y 向上、XZ 地面、Z 正方向指向玩家；模型和 Collider 单位一致；调试层可显示碰撞几何。
  5. 环体不可用实心盘状 Collider 冒充；不能仅靠二维距离阈值判套中；碰撞必须阻挡非法侧穿。
  6. Goose 视觉动画与物理 Collider 每个物理步同步，前后不一致时暂停相关功能，先修问题。
  7. 正式模式的成功累计应有幂等写入和恢复机制；练习投掷绝不计正式累计。
  8. 真实动物虐待、恐慌尖叫、勒颈/受伤表现不可加入。
  9. UI 横屏适配，不挡投掷热区与鹅头颈；触摸和鼠标同逻辑，但最终手感以真机为准。
  10. 任何外部资源/图片/音频注明来源与许可；原型可全部用灰盒几何占位。
  11. 未实际执行的命令/测试不得写“通过”；失败时附最小复现、可能原因、未解决项。
  12. 每阶段完成后提交一份 report.md 或控制台总结：实现内容、文件、命令与结果、截图/录屏位置、风险、下一步；等待人工验收，不自动进入下一个阶段。

完成定义（DoD）

  • npm run build 成功；必要的 npm run test 用例通过；类型检查无新错误。
  • 可用 H5 链接/本地预览复现；操作者能够按清单实测成功和失败路径。
  • Debug 面板、碰撞线框、相关数值可观察；不得用视觉假象掩盖判定错误。
  • 文档和参数同步；不擅自修改 GDD 已确认的玩法。
