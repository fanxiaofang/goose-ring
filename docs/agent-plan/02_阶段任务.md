# 02 Agent 执行任务与阶段关口（P0–P2）

**执行原则：完成一个、验收一个、再开始下一个。** 下列任务顺序是实现依赖，不是玩家关卡。对应 GDD v1.1 的 P0–P2，不意味着 P3/P4 已定或已开发。

v0.3 阶段顺序为 **P0-0 → P0-1 → P0-L → P0-A → P0-2 → P0-3 → P1 → P2**。P0-0/P0-1 已完成，P0-L/P0-A 已验收；**P0-2 已由项目负责人于 2026-11-27 最终签收**，当前下一阶段为 **P0-3**。已签收阶段保留既有实现、测试记录和人工证据，不作为当前任务重新执行。

## 通用交付要求

每个任务结束，Agent 必须汇报：

1. 本次实际改动文件与功能；如修改既有结构，说明为何必要。
2. 启动/构建/测试的**真实命令及输出摘要**；做不到的明确写原因。
3. 如何人工复现正例、反例；提供至少 2 张截图或说明录屏保存位置（如果执行环境允许）。
4. 可调参数清单、未解决问题和实际风险。
5. 停在当前阶段，不自动进入下一阶段。

每步确保 Git 可回退；**失败路径也是验收目标**。

## P0-0：创建工程、横屏场景与物理底座（已实现，供追溯）

**目标**：证明 Three.js + Rapier + Vite 在 H5 本地正常运行。

**范围（历史实施记录）**：初始化 `vanilla-ts`；创建 Three scene、相机实验（当时含正交视角）、地面、围栏（视觉与 Collider 同步）、Rapier WASM 初始化、固定时间步主循环、基础调试面板、鼠标/触控基本事件；屏幕不是横屏时提示旋转。当前正式默认相机以 P0-L 已验收的透视 FOV30°为准，正交仅作调试。

**排除**：没有鹅 AI、没有玩法、没有广告/商店/UI 大厅、没有正式美术。

**验收**：浏览器桌面/移动模拟可见宽围栏；调整镜头不破坏坐标；物理地面碰撞有效；`npm run build` 与 TS 检查通过；控制台无持续错误；开发态能看物理碰撞调试信息。

**关口**：能安全生成一个测试刚体落到地面，不穿透；若 Rapier WASM 加载失败，先修再继续。

## P0-1：套圈真实物理与飞行操作（已实现，供追溯）

**目标**：可投掷一个具有空孔、体积与倾角的物理圈。

**范围**：有孔环体复合 Collider；出手初速度；重力、摩擦、弹性、弹跳和碰栏；底部拖拽/松手投掷；发射起点；圈的销毁回收；显示固定步、环体 Collider、速度与旋转，必要时 CCD。

**排除**：此时暂不判断套中；不加复杂鹅模型。

**验收**：多种力度可产生连续可重复的飞行距离；碰地有响应、碰围栏可弹/停且不透明穿透；圈穿过无障碍空洞时不被假圆盘挡住；多次投掷后资源清理正常；不能把视觉圈做得和 Collider 明显不一致。

**关口**：P0-1 至少录下 3 种碰撞情形（地面、栏杆、不同初始倾角）。现存测试与证据见 [04 P0-0/P0-1 参数表和 D-20261123-009](04_决策与参数.md)。后续按 v0.2 进入 P0-L。

## P0-L：手机横屏场景布局验收

**目标**：在 844×390 和 667×375 手机横屏与非对称安全区内，完整看到围栏、八只鹅的头颈、投掷线和手持圈，上方入口与下方操作有独立空间。

**范围**：按 [05 布局规范](05_主游戏场景构图与布局执行规范.md) 实现全屏 Canvas、Play Rect 取景、顶部入口/HUD、底部起手区与仅大厅使用的右侧广告灰盒。使用现有世界尺度和物理参数，以透视（垂直 FOV30°、俯视30°、偏航0°）为默认。验收大厅的模式卡与资源入口，以及投掷场的正式 HUD 状态（练习已降级为调试直达，不再作为玩家 HUD 验收项）。容量和摊主活动带按评审结果纳入后续资产预算。

**关口**：[PL-01～PL-07](03_验收测试.md#2-p0-l-手机横屏布局矩阵) 给出两个尺寸测量与截图、非对称安全区和真机触摸证据，并走通正式场末圈结算回大厅、暂停后继续、提前结束及取消。对照未达标时记录是哪项及实测值。由项目负责人验收后再进入 P0-A。实际退币、广告接入和完整战绩统计列入后续阶段。

## P0-A：投掷可达性与操作映射

**目标**：以 P0-L 确认的构图，验证按住计时、下拉或斜拉蓄力、向前甩投三种方式，打通出手、预览、Rapier 实投与八个静态鹅位的可达链路。

**实施顺序**

1. 沿用 P0-L 构图和两个起手区。复跑静态场三档随机站位的八鹅样本及原站位回归，记录当前发射参数、基线碰撞和余量，再决定是否需要改物理参数。
2. 在现有输入上加入三种手势的意图锁定、释放与取消，复用同一发射映射、轨迹预览和重放参数。保留暂停、扣圈、末圈结算和单鹅调试直达入口，验证缩短视口及底带起手是否还有足够下拉行程。
3. 用正常手势可生成的输入逐只验证真实环孔下降越过鹅头并进入颈区，并测邻近输入与失败对照。若需调整，先按输入行程、出手参数与障碍分别定位，按同一批记录做单变量比较。

**关口**：[PA-01～PA-05](03_验收测试.md#3-p0-a-投掷可达性矩阵) 留 8 只鹅的投掷记录、正反例、失败原因和真机输入证据。自动重放与真机结果分别记录。任一正式目标缺少可重现入口或基本操作容差时交人工决策。P0-2 引入稳定期和正式套中状态。执行细节见 [P0-A 提示词](prompts/P0-A_投掷可达性与操作映射.md)。

## P0-2：几何鹅头/颈 + RingJudge 状态机

**目标**：实现**只有合理地套入鹅颈才算成功**。

**范围**：几何头（球形）、颈（胶囊/圆柱）、身体，Collider 与视觉对应；`RingJudge` 状态机；头部上方→颈部的穿越事件；稳定时间；合法/非法命中；开发态日志、测试场景。

**排除**：暂不做复杂 AI、精美鹅或历史累计。

**验收用例**：

- 正面落入、环内孔满足尺寸、稳定超过配置时长 → 成功 1 次。
- 直接碰头、碰身、环边擦过 → 不成功。
- 环从侧面穿到脖子/从背后穿模 → 不成功、并可解释为何。
- 在稳定期滑落 → 不成功。
- 一个环碰到两个鹅 → 最多 1 次有效成功。
- 同一次 throwId 多次接触事件 → 只结算 1 次。

**关口**：**至少 5 种**可手动触发的正反场景有文字/截图证据；若判定不得不采用近似方案，必须标明真实物理和规则补偿的边界。

> **状态（2026-11-27，负责人最终签收）**：`RingJudge` 已实现（稳定期 0.25 s 起步、一投一只、最早入颈优先、退场鹅不再作为目标），5 类正反场景与八鹅名义投掷由 `ringJudge.test.ts` 25 项自动化覆盖，最终全量 106 项通过；`?judge=1` 可观察状态机。真机确认：正例套中计数正确、无幽灵锁定。验收记录见 [report](report.md) 与 [03 PH-04~PH-09](03_验收测试.md)。决策见 04 D-20261126-008。104 项是增加退场鹅排除用例前的中间记录。

## P0-3：鹅头颈动作、动态 Collider 同步与压力测试

**目标**：证明鹅头颈运动时，视觉姿态、Rapier Collider 与 RingJudge 使用的目标位姿在同一固定物理步保持一致；动态鹅仍能被合理套中，鹅/鹅和鹅/围栏主要碰撞边界不出现明显穿模。

**实施顺序**：
1. **P0-3A 单鹅动作**：仅在现有灰盒鹅上实现低头、抬头、左歪头、右歪头四种可预测、可重放的预设动作；不做随机漫游和躲避 AI。
2. **P0-3B 姿态单一数据源**：建立逐物理步姿态快照，供 Three.js 网格、Rapier 运动学目标/Collider 与 RingJudge 共用；明确 tick 和更新顺序，避免一 tick 延迟。
3. **P0-3C RingJudge 动态目标**：将构造时预计算的静态头/颈目标改为每个固定步读取实时姿态；保留上一 tick/当前 tick 穿越历史。
4. **P0-3D 有限碰撞边界**：验证一只运动鹅与静态鹅、围栏的主要碰撞关系；先说明 Rapier 刚体类型与响应语义，不能把静态重叠或仅接触事件当成阻挡成功。
5. **P0-3E 压力与画面回归**：100 次连续投圈；渲染 30/15 FPS 模拟但物理保持固定步；验证暂停/恢复/切后台；在 844×390、667×375 的 P0-L 已验收 FOV30°镜头下检查头颈和圈的可读性。

**保护约束**：不得重做 P0-2 判定，不得擅自改变内孔、颈轴容差、下降方向、静止兜底、稳定期 0.25 s 起步、75°倾斜容忍、一投一只、同 tick 选择和退场鹅排除。若动态姿态暴露判定边界，提供 seed、tick、姿态与反例，交负责人决策。

**验收**：
- PH-10：四种动作中，视觉、Collider 与 RingJudge 目标位姿逐物理步一致。
- PH-11：运动鹅与静态鹅/围栏的主体边界有可验证的阻挡或约束；记录最小分离距离、最大穿透深度、修正次数。
- PH-12：100 次可重复投圈、15/30 FPS 渲染模拟、暂停与后台恢复；记录穿模、误判、重复结算、物理耗时和复现 seed。
- P0-2 正反例、幂等、多鹅竞争和退场鹅排除全部回归。

**关口**：报告真实命令与输出、测试表、截图/录屏、seed、异常次数和未测试项。任何明显穿模或命中假象都先停下定位。项目负责人签收后才能进入 P1。

## P2：正式游戏核心闭环（不接真实广告）

**目标**：正式套中立即记 1 只、保存、支持清摊和跨天继续。

**范围**：静态/普通/机灵模式，各自独立 Board，按所选场次兑换单场券；每盘初始 8 鹅（可调）；基础漫游、察觉/反应延迟/躲避冷却（按 GDD 的参数原型）；一次投掷对应唯一 throwId；`CAUGHT` 在单次原子本地事务更新玩家历史累计和盘面；清摊/漂亮清摊；换盘、切模式、暂停恢复；个人准确率、按模式总数；简单大厅/HUD/结算卡；币和兑换**配置化模拟**（可根据进度独立开关，不引入真实广告）。

**不做**：摊主指挥、完整 Boids、真实排行、真实微信/抖音 SDK、朋友圈立即分享领币、省份榜。

**验收**：

- 静态/普通/机灵鹅套中 → 对应累计 +1、总数 +1。
- 单鹅调试直达套中 → 正式累计、正式 Board 与正式圈库存完全不变。
- **单只正式套中后立即刷新** → 历史数据和 Board 一致。
- 重复触发一次 hit → 不能双加；换盘和清摊不能二次加数。
- 8/8 清摊 → 清摊次数 +1，累计不额外 +8；可新盘。
- 中途退出明天再来 → 继续同一盘、库存和已套中保持。
- 圈耗尽且未清摊 → 可用试玩币补圈并续同一盘。余额不足显示差额，可领取试玩币后回到原档位，或保留鹅盘回大厅。末圈清摊时优先出清摊结果。
- 余额兑换同一命令重复执行 → 不得重复送圈或扣币；P2 仅模拟政策。

**关口**：P2 才成为内部 H5 玩法原型。即使 P2 通过，也不能声称已满足微信/抖音发布条件。
