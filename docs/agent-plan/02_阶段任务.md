# 02 Agent 执行任务与阶段关口（P0–P2）

**执行原则：按依赖推进，但优先让核心玩法尽快可玩；每阶段只做足以证明目标成立的必要验收。** 下列任务顺序是研发关口，不是玩家关卡。

v0.3.1 顺序为 **P0-0 → P0-1 → P0-L → P0-A → P0-2 → P0-3 → WX-0 → P0-4 → P1 → P2 → P3 → P4 → P5**。P0-0/P0-1 已完成，P0-L/P0-A 已验收；**P0-2 已由项目负责人于 2026-11-27 最终签收**，当前下一阶段为精简版 **P0-3**。已签收阶段保留既有实现、测试记录和人工证据，不作为当前任务重新执行。

## 通用交付要求

每个任务结束，Agent 必须汇报：

1. 本次实际改动文件与功能；如修改既有结构，说明为何必要。
2. 本阶段真正执行的命令及结果；未执行项明确标注，不照抄历史结果。
3. 最小正例/反例复现方式；有价值时提供截图/录屏，不为凑数量制作材料。
4. 未解决问题、风险和回退方法。
5. 停在当前阶段，不自动进入下一阶段。

每步确保 Git 可回退；**测试数量按风险和目标决定，不以测试数量作为阶段成果。**

## P0-0：创建工程、横屏场景与物理底座（已实现，供追溯）

**目标**：证明 Three.js + Rapier + Vite 在 H5 本地正常运行。

**范围（历史实施记录）**：初始化 `vanilla-ts`；创建 Three scene、相机实验（当时含正交视角）、地面、围栏（视觉与 Collider 同步）、Rapier WASM 初始化、固定时间步主循环、基础调试面板、鼠标/触控基本事件；屏幕不是横屏时提示旋转。当前正式默认相机以 P0-L 已验收的透视 FOV30°为准，正交仅作调试。

**排除**：没有鹅 AI、没有玩法、没有广告/商店/UI 大厅、没有正式美术。

**验收**：浏览器桌面/移动模拟可见宽围栏；调整镜头不破坏坐标；物理地面碰撞有效；`npm run build` 与 TS 检查通过；控制台无持续错误；开发态能看物理碰撞调试信息。

**关口**：能安全生成一个测试刚体落到地面，不穿透；若 Rapier WASM 加载失败，先修再继续。

## P0-1：套圈真实物理与飞行操作（已实现，供追溯）

**目标**：可投掷一个具有空孔、体积与倾角的物理圈。

**范围**：有孔环体复合 Collider；出手初速度；重力、摩擦、弹性、弹跳和碰栏；底部拖拽/松手投掷；发射起点；圈的销毁回收；显示固定步、环体 Collider、速度与旋转，必要时 CCD。

**排除**：此时暂不判断套中；不加复杂鹅模型。

**验收**：多种力度可产生连续可重复的飞行距离；碰地有响应、碰围栏可弹/停且不透明穿透；圈穿过无障碍空洞时不被假圆盘挡住；多次投掷后资源清理正常；不能把视觉圈做得和 Collider 明显不一致。

**关口**：P0-1 至少录下 3 种碰撞情形（地面、栏杆、不同初始倾角）。现存测试与证据见 [04 P0-0/P0-1 参数表和 D-20261123-009](04_决策与参数.md)。后续按 v0.2 进入 P0-L。

## P0-L：手机横屏场景布局验收

**目标**：在 844×390 和 667×375 手机横屏与非对称安全区内，完整看到围栏、八只鹅的头颈、投掷线和手持圈，上方入口与下方操作有独立空间。

**范围**：按 [05 布局规范](05_主游戏场景构图与布局执行规范.md) 实现全屏 Canvas、Play Rect 取景、顶部入口/HUD、底部起手区与仅大厅使用的右侧广告灰盒。使用现有世界尺度和物理参数，以透视（垂直 FOV30°、俯视30°、偏航0°）为默认。验收大厅的模式卡与资源入口，以及投掷场的正式 HUD 状态（练习已降级为调试直达，不再作为玩家 HUD 验收项）。容量和摊主活动带按评审结果纳入后续资产预算。

**关口**：[PL-01～PL-07](03_验收测试.md#2-p0-l-手机横屏布局矩阵) 给出两个尺寸测量与截图、非对称安全区和真机触摸证据，并走通正式场末圈结算回大厅、暂停后继续、提前结束及取消。对照未达标时记录是哪项及实测值。由项目负责人验收后再进入 P0-A。实际退币、广告接入和完整战绩统计列入后续阶段。

## P0-A：投掷可达性与操作映射

**目标**：以 P0-L 确认的构图，验证按住计时、下拉或斜拉蓄力、向前甩投三种方式，打通出手、预览、Rapier 实投与八个静态鹅位的可达链路。

**实施顺序**

1. 沿用 P0-L 构图和两个起手区。复跑静态场三档随机站位的八鹅样本及原站位回归，记录当前发射参数、基线碰撞和余量，再决定是否需要改物理参数。
2. 在现有输入上加入三种手势的意图锁定、释放与取消，复用同一发射映射、轨迹预览和重放参数。保留暂停、扣圈、末圈结算和单鹅调试直达入口，验证缩短视口及底带起手是否还有足够下拉行程。
3. 用正常手势可生成的输入逐只验证真实环孔下降越过鹅头并进入颈区，并测邻近输入与失败对照。若需调整，先按输入行程、出手参数与障碍分别定位，按同一批记录做单变量比较。

**关口**：[PA-01～PA-05](03_验收测试.md#3-p0-a-投掷可达性矩阵) 留 8 只鹅的投掷记录、正反例、失败原因和真机输入证据。自动重放与真机结果分别记录。任一正式目标缺少可重现入口或基本操作容差时交人工决策。P0-2 引入稳定期和正式套中状态。执行细节见 [P0-A 提示词](prompts/P0-A_投掷可达性与操作映射.md)。

## P0-2：几何鹅头/颈 + RingJudge 状态机

**目标**：实现**只有合理地套入鹅颈才算成功**。

**范围**：几何头（球形）、颈（胶囊/圆柱）、身体，Collider 与视觉对应；`RingJudge` 状态机；头部上方→颈部的穿越事件；稳定时间；合法/非法命中；开发态日志、测试场景。

**排除**：暂不做复杂 AI、精美鹅或历史累计。

**验收用例**：

- 正面落入、环内孔满足尺寸、稳定超过配置时长 → 成功 1 次。
- 直接碰头、碰身、环边擦过 → 不成功。
- 环从侧面穿到脖子/从背后穿模 → 不成功、并可解释为何。
- 在稳定期滑落 → 不成功。
- 一个环碰到两个鹅 → 最多 1 次有效成功。
- 同一次 throwId 多次接触事件 → 只结算 1 次。

**关口**：**至少 5 种**可手动触发的正反场景有文字/截图证据；若判定不得不采用近似方案，必须标明真实物理和规则补偿的边界。

> **状态（2026-11-27，负责人最终签收）**：`RingJudge` 已实现（稳定期 0.25 s 起步、一投一只、最早入颈优先、退场鹅不再作为目标），5 类正反场景与八鹅名义投掷由 `ringJudge.test.ts` 25 项自动化覆盖，最终全量 106 项通过；`?judge=1` 可观察状态机。真机确认：正例套中计数正确、无幽灵锁定。验收记录见 [report](report.md) 与 [03 PH-04~PH-09](03_验收测试.md)。决策见 04 D-20261126-008。104 项是增加退场鹅排除用例前的中间记录。

## P0-3：最小活动头颈与动态判定同步（当前下一阶段）

**目标**：只证明一只鹅的头颈动起来以后，视觉姿态、Rapier Collider 与 RingJudge 使用同一份实时姿态；玩家仍能通过真实投圈套中或合理失败。

**范围**：
1. 在现有灰盒鹅上实现低头、抬头、左歪头、右歪头四种可预测动作。
2. 建立 `GoosePoseSnapshot`，作为视觉网格、头颈 Collider、RingJudge 的唯一姿态来源。
3. 将 RingJudge 从创建时固定目标改为每个固定物理步读取实时头颈位置。
4. 只验证实现动态头颈必需的碰撞边界；不做鹅群漫游、察觉、躲避和完整群体碰撞。
5. 保留最小的美术/物理分离约定：外观网格不能直接决定命中；以后换模型仍由同一份姿态锚点驱动物理代理。

**不做**：100 次连续投圈、15 FPS/30 FPS 大矩阵、完整暂停/切后台压力矩阵、正式 GLB、美术骨骼、Boids、普通/机灵场 AI、存档、经济和平台 SDK。

**最小实施顺序**：
1. **P0-3A 姿态**：四种固定、可重放头颈动作。
2. **P0-3B 同源快照**：定义逐物理步姿态数据和明确更新顺序，视觉/Collider/RingJudge 不得各算各的。
3. **P0-3C 动态判定**：保留上一 tick 与当前 tick 的姿态历史，按 P0-2 已签收规则处理穿越证据。
4. **P0-3D 最小碰撞与调试**：动态头颈 Collider 不出现明显脱离视觉的情况；调试层能同时显示鹅、Collider、RingJudge 目标。
5. **P0-3E 美术兼容约定**：只写清语义锚点和物理代理边界，不制作模型、不做双模型兼容测试。

**保护约束**：不得重做 P0-2 判定，不得擅自改变内孔、颈轴容差、下降方向、静止兜底、稳定期 0.25 s 起步、75°倾斜容忍、一投一只、同 tick 选择和退场鹅排除。若动态姿态暴露判定边界，提供最小复现和数据，交负责人决策。

**最小验收**：
- PH-10：四种头颈动作中，视觉、Collider 与 RingJudge 目标使用同一 tick 姿态。
- PH-11：动态头颈下至少一个真实套中正例和一个明确失败反例；结果符合 P0-2 规则。
- PH-12：在正式 FOV30°镜头下检查动态鹅头颈/圈可读性；无明显头颈 Collider 脱离或瞬移。
- 只新增必要的姿态/判定定向测试；阶段结束执行一次 typecheck、build 和相关回归。若改动触及 RingJudge/PhysicsWorld，阶段结束再运行一次完整现有自动化套件即可，不在每个小步骤重复。
- 不要求 100 次连续投圈或长时间性能压力测试；发现实际性能问题再增加针对性测量。

**关口**：交付影响文件、四种动作画面、一个动态正例、一个动态反例、相关测试真实输出和未测试项。项目负责人签收后再进入 WX-0。

## WX-0：微信小游戏运行环境与包体短验证（P0-3 后立即做）

**目标**：用最小场景尽早确认当前 Three.js + Rapier 技术路线能否进入微信小游戏运行环境，并获得真实包体数据；不是完整平台发布。

**范围**：
- 用微信开发者工具打开最小适配构建，确认 Canvas/WebGL、Three.js 渲染、Rapier WASM 初始化、触摸输入、基础资源读取和本地存储。
- 检查 H5 DOM HUD 是否需要替换为 Canvas/小游戏 UI；只验证最小必要界面，不重做完整 UI。
- 记录主包、每个分包、总包、远程资源大小和开发者工具校验结果；按当前微信官方规则确定硬限制，项目预算至少留 20% 余量。
- 若当前缺少 AppID/开发者工具权限，明确记录阻塞，不得假称已完成微信真机验证。

**不做**：广告、分享、真实排行榜、登录、支付、完整大厅和正式上架审核；抖音适配也不在此阶段。

**验收**：最小 3D 场景能在微信开发者工具运行；Rapier WASM 能加载；能完成一次触摸投圈或等价输入；有实际包体记录和兼容性问题清单。若技术路线遇到阻塞，先给出最小修复方案，不重写整套引擎。

## P0-4：普通场与机灵场活动鹅核心玩法

**目标**：把“鹅会走、会察觉、会躲圈”做成真实可玩的核心玩法。普通场和机灵场共用同一套轻量 AI，只通过参数形成难度差异。

**范围**：
1. 先支持 8 只灰盒鹅；所有鹅复用同一份模型/几何资源和动画逻辑。
2. 基础漫游：鹅在围栏内选择局部目标，走走停停；边界回避；邻近鹅做简单分离，避免明显重叠。先不用完整 Boids。
3. 投圈威胁判断：根据投圈轨迹估算是否进入鹅的附近威胁区域。
4. 行为链：察觉概率 → 个体反应延迟 → 低头/左躲/右躲等可见动作 → 躲避冷却。
5. 普通场与机灵场使用同一 AI，只调整察觉率、反应延迟、躲避速度/幅度和冷却等配置；机灵场更难，但不能瞬移或每次必中躲避。
6. 使用独立 seed 让行为可复现；不同鹅有轻微个体差异，不得全员同步。

**不做**：摊主指挥、赶鹅按钮、完整 Boids、复杂性格树、多品种模型、最终美术、服务端排行和广告。

**最小验收**：
- 普通场鹅会在围栏内自然走动，边界和相邻鹅之间无明显穿模。
- 普通场存在“没察觉/反应慢/成功躲避”等不同结果。
- 机灵场在相同或可比输入下明显更敏锐，但仍存在可抓住的投掷时机。
- 玩家能观察到鹅的动作前兆；不允许最后瞬间瞬移。
- 至少各做一条可重放的普通场与机灵场行为样本；负责人实际试玩两种模式，确认差异可感知。
- 只做针对行为状态、威胁判断和边界约束的必要测试；不做 100 次压力测试。

## P1：静态/普通/机灵三模式核心可玩闭环

**目标**：让三个玩家模式都能从大厅进入、投圈、套中、清摊或重新开始，形成可以连续试玩的核心游戏。

**范围**：
- 静态场沿用已完成的固定鹅玩法；普通场和机灵场接入 P0-4 活动鹅。
- 三个模式各自独立初始化鹅盘；每盘暂定 8 只鹅；切换模式不串用鹅的行为配置或盘面。
- 套中鹅按既定规则友好退场，当前盘计数即时 +1；全部套完可清摊，再开新盘。
- 保留现有投掷手势、轨迹辅助规则、HUD 和暂停/结束流程；只补齐三个模式之间缺失的入口与状态衔接。
- 使用开发态圈数或现有资源流程完成试玩，不因币、广告、登录或在线排行阻塞玩法验证。

**不做**：新手分步教学、完整历史存档、币/圈经济、真实广告、在线排行榜、分享奖励、好友 PK。

**最小验收**：
- 静态/普通/机灵三个模式均可进入、投圈、套中和重新开盘。
- 静态鹅不移动；普通鹅和机灵鹅的行为差异可感知。
- 三个模式的盘面与统计不串场；单鹅调试直达不进入玩家模式、不污染正式记录。
- 每种模式至少人工完成一轮短试玩；不要求每个模式跑大规模自动化压力测试。

## P2：新手引导、基础存档与经济模拟

**目标**：在三模式核心玩法已经成立后，补上新手理解、跨次游玩和资源循环。

**范围**：
- 静态场承担首次教学：起手区 → 方向 → 力度 → 松手；提供轨迹/落点辅助。
- 本地版本化存档：历史累计、静态/普通/机灵分模式累计、各模式 Board、清摊数和准确率；套中即时幂等写入。
- 币/圈兑换、每日领取等仅做可配置本地模拟；单鹅调试与正式资源隔离。
- 月榜/历史榜先做数据口径和界面占位，不伪造在线排名；真实在线排行后续接可信服务端。

**不做**：真实广告 SDK、分享奖励、支付、全服榜单后端。

## P3：美术与庙会氛围升级

使用可合法商用的免费素材或 AI 生成模型作为候选；不要求项目负责人手工 Blender 建模。优先复用同一鹅模型、骨骼和贴图；美术网格适配既有物理代理与姿态锚点。只在风格方向明确且三模式玩法成立后，才投入正式角色、摊主、场景和音频资源。

## P4：微信首发适配与发布准备

在 WX-0 的验证基础上，完成微信平台 Adapter、正式包体拆分/资源加载、触摸/生命周期/音频/存储适配、微信广告与分享规则核验、真实排行榜服务和审核检查。发布前在微信开发者工具与真实设备验证运行、性能、内存和包体；不得以 H5 构建成功代替微信验收。

## P5：抖音小游戏后续适配

微信首发核心玩法稳定后，复用游戏核心，单独实现 Douyin Adapter 并验证运行时、资源、包体、广告、分享、排行和审核规范。不提前为抖音复制游戏逻辑，也不阻塞当前开发。
