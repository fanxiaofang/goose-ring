## P0-3 开工前检查

- 阅读当前代码中的 `GoosePlaceholder`、`PhysicsWorld`、`RingJudge`、`GameApp` 和 `gameConfig`，以实际文件为准。
- 核对当前鹅的视觉姿态、Rapier 刚体/Collider、RingJudge 目标坐标是否来自同一份姿态数据。
- 当前已知基线：灰盒鹅尚无头颈动画；`PhysicsWorld` 为鹅创建 fixed 刚体及身体球/颈胶囊/头球 Collider；`RingJudge` 构造时根据布局预计算头颈世界位置；`GameApp` 当前固定步顺序为物理 step 后读取接触并推进判定。P0-3 的核心就是在不破坏 P0-2 语义的前提下建立实时姿态同步。
- 先执行并记录适用的基线命令：`npm run typecheck`、`npm run test -- --pool=threads`、`npm run build`。实际结果以本次执行为准，不照抄历史报告。
- 提交 P0-3 影响文件清单、姿态数据方案、物理更新顺序、碰撞响应策略、PH-10～PH-12 验收方法和风险。按项目工作流等待负责人确认实施方案后再修改代码。

## P0-3 范围与保护

只做一个可预测运动的灰盒鹅头颈、头/颈动态 Collider、RingJudge 实时目标位姿、必要的鹅/围栏阻挡验证、低帧率/暂停/恢复与 100 次压力测试。必须保留 P0-L 的 FOV30°构图、P0-A 的投掷映射和 P0-2 的 RingJudge 判定规则。

不得擅自改变圈的尺寸/质量/初速度、稳定期 0.25 s、倾斜容忍 75°、入颈几何条件、一投一只或退场鹅排除逻辑。若动态姿态下暴露判定问题，先提供固定 seed、物理 tick、目标姿态和最小复现，提出差异，不得直接放宽阈值。

## 交付与停点

完成后更新测试矩阵和阶段报告，列出改动文件、真实命令/输出、100 次投掷的异常计数、最差穿透/分离数据、重现 seed、两种手机视口截图/录屏、未测试项和剩余风险。**完成后停在 P0-3，等待项目负责人人工验收；不得自动进入 P1。**
