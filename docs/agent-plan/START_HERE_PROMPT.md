## P0-3 开工前检查

- 阅读当前代码中的 `GoosePlaceholder`、`PhysicsWorld`、`RingJudge`、`GameApp` 和 `gameConfig`，以实际文件为准。
- 核对当前鹅的视觉姿态、Rapier 刚体/Collider、RingJudge 目标坐标是否来自同一份姿态数据。
- 当前已知基线：灰盒鹅尚无头颈动画；`PhysicsWorld` 为鹅建立 fixed 刚体及身体球/颈胶囊/头球 Collider；`RingJudge` 构造时根据布局预计算头颈世界位置；`GameApp` 当前固定步顺序为物理 step 后读取接触并推进判定。
- 先提交简短的影响文件清单、姿态数据方案、固定步更新顺序和回退方法。不要先写几十项测试计划，不得修改 P0-2 已签收语义。
- 测试规模遵循风险：只为新动态姿态添加定向用例；完成时做一次 typecheck、build 和必要的核心回归。**不要求 100 次连续投圈，不要求每个小改动都跑全量 106 项。**

## P0-3 范围与保护

只做一个灰盒鹅的低头、抬头、左歪头、右歪头预设动作；建立 `GoosePoseSnapshot`；让视觉、Collider、RingJudge 使用同一物理 tick 的姿态；验证动态动作下至少一个套中正例和一个失败反例；检查鹅头颈与围栏/身体没有明显穿透。不得在 P0-3 实现完整漫游、察觉、躲避或普通/机灵模式 AI。

必须保留 P0-L 的 FOV30°构图、P0-A 的投掷映射和 P0-2 的 RingJudge 判定规则。不得擅自改变圈的尺寸/质量/初速度、稳定期 0.25 s、倾斜容忍 75°、入颈几何条件、一投一只或退场鹅排除逻辑。

## 微信包体与技术风险

- 当前 H5 的 Vite 构建警告/单 chunk 体积不能直接等同于微信主包大小，但必须作为风险信号跟踪。
- WX-0 记录微信开发者工具实际显示的主包、分包、总包体积；限制以当前微信官方文档和上传校验为准，不照搬旧教程中的数字。
- 任何资源预算都要留余量；8 只鹅共用同一模型/动画/贴图，不复制 8 份；三个模式复用同一套逻辑和资源。
- 微信适配要检查小游戏运行时没有完整浏览器 DOM 的情况；H5 DOM HUD 不可视为可直接发布。
- 游戏核心不得直接调用 `wx.*`；平台能力通过 Adapter/Port 接入。抖音本阶段不做。
